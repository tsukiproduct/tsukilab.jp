# A+AT仕様 パチスロアプリ 開発仕様書

- 版数: v1.0（初版）
- 対象: オリジナルA+AT機シミュレーターアプリ
- 前提: 実機の内部抽選方式（16bit乱数／分母65536）を忠実に再現する

---

## 1. コンセプト

### 1.1 ゲーム性の骨子
「リアルボーナス（A）で出玉の主軸を作り、低純増AT で出玉を伸ばす」王道のA+AT構成。

- 通常時: リーチ目・演出でボーナスを察知する「出目で遊ぶ」ゲーム性
- BIG中: 技術介入（ビタ押し）でATゲーム数を獲得
- AT中: 純増+0.5枚/GでじわじわG数を消化しつつ、AT中のボーナスでループを狙う

### 1.2 出玉サイクル
```
通常時 ──ボーナス当選──▶ BIG/REG
   ▲                        │
   │                 BIG中ビタ押しでAT G数獲得
   │                        ▼
   └──AT終了────── AT（純増+0.5枚/G）
                            │
                     AT中ボーナスで再セット（ループ）
```

### 1.3 テーマ・世界観
本仕様ではシステムを規定し、図柄デザイン・キャラクター・演出テーマは別途アートディレクション工程で決定する（自社オリジナルIPでのスキニングを想定。図柄名は本書ではプレースホルダー表記）。

## 5. 内部抽選仕様（本仕様書の核）

### 5.1 抽選方式
1. レバーオンの瞬間に 0〜65535 の乱数を1個取得する（毎ゲーム独立・完全確率)
2. 現在の設定・内部状態に対応する抽選テーブルを参照する
3. **減算方式**で成立役を決定する: 乱数から各行のカウントを上から順に減算し、負になった行のフラグが成立役

```
擬似コード:
rnd = getRandom16bit()          // 0..65535
for row in table:
    rnd -= row.count
    if rnd < 0: return row.flag
return HAZURE                    // 理論上到達しない（合計=65536のため）
```

### 5.2 実装上の必須ルール
- 各設定のテーブルは**全行合計が必ず65536**。起動時にassertで検証し、不一致なら例外停止
- 乱数は `crypto.getRandomValues(new Uint16Array(1))` 相当の一様乱数を使用（`Math.random`の下位ビット偏りを回避）
- 小役+ボーナスの**重複当選は独立した1行**として定義する（「小役成立後に二次抽選」方式は採らない）
- ボーナスフラグは入賞まで**持ち越し**。持ち越し中は「内部中テーブル」（§5.5）に切り替える

### 5.3 内部抽選テーブル（設定1〜6・カウント値）

単位はすべて「65536中の個数」。合計は全設定で65536（検算済み）。

設定推測要素の設計意図:
- **REG確率**に大きな設定差（設1:設6 ≒ 1.78倍）→ 主要判別要素
- **チェリー+REG重複**（24→64）→ カウント推奨要素
- **1枚役**に緩やかな設定差 → 補助要素
- リプレイ・ベル・スイカ単独は全設定共通 → ノイズ排除

### 5.5 内部中テーブル（ボーナス持ち越し中）
ボーナス成立後〜入賞までの間は、上表から**全ボーナス行をハズレに置換**したテーブルを使用する（小役のカウント値は不変）。これにより持ち越し中も小役確率が変わらない実機挙動を再現する。

### 5.6 二次抽選（AT・演出系）
成立役を契機とする二次抽選は**分母256**（2の8乗）で統一する。

| 契機 | 抽選内容 | 当選値（/256） |
|---|---|---|
| BIG入賞時 | フリーズ発生 | 4（1/64） |
| リーチ目役+BIG | 上位BIG（AT確定BIG）昇格 | 64（25%） |
| AT中スイカ | ATゲーム数+10G | 128（50%） |

## 6. リール制御仕様

### 6.1 引き込み優先順位
```
リプレイ ＞ 小役 ＞ ボーナス
```
- リプレイ成立時は必ずリプレイを引き込む
- 小役成立時は小役を最優先（ボーナス持ち越し中でも小役優先）
- ボーナスフラグのみ成立（または持ち越し中のハズレ）のとき、ボーナス図柄を4コマ以内で引き込み可能なら引き込む

### 6.2 制御テーブル方式
- 「成立フラグ × 押下位置（21箇所） × リール」→ 停止位置 のテーブル参照方式
- ハズレ時は小役・ボーナスがテンパイしない「安全な出目」に制御
- ボーナス成立時のみ停止し得る出目＝**リーチ目**を制御表レベルで定義する（目標: 数百通り以上）

### 6.3 ペナルティ
- 通常時は左リール第1停止を推奨手順とし、変則押し時はAT関連の二次抽選を無効化（メイン抽選には影響させない）

## 8. AT仕様

| 項目 | 仕様 |
|---|---|
| 名称 | 仮称「MOON TIME」（テーマ決定後に正式名称） |
| 性能 | 純増 約+0.5枚/G（リプレイ高確率+押し順ベルナビ） |
| 突入契機 | BIG終了時50%（+設定微差 各設定+0.4%刻み）／BIG中ビタ押しG数獲得時は確定／REG中抽選 |
| 初期G数 | 40G + BIG中獲得分（ビタ押し3回成功で最大+30G） |
| 上乗せ | AT中スイカで50%で+10G（§5.6） |
| AT中ボーナス | メインテーブルは通常時と同一（ボーナス確率不変）。AT中のBIGは技術介入不要で+30G固定 |
| 終了条件 | 残りG数0 ／ 有利区間相当の上限（差枚+2400枚 or 1500G）で完走終了 |
| 平均継続 | 約70G（ループ込み期待値） |

設計思想: AT自体の出玉は控えめにし、「AT中にボーナスを引いて延命する」ヒキ勝負のループ構造とする。メインの65536テーブルはAT中も不変（抽選の公平性・実機らしさを担保）。

## 9. 状態遷移

```
[通常時] --ボーナス当選--> [内部中] --入賞--> [BIG/REG中]
                                                  │
                    AT非当選                      │AT当選/G数獲得
[通常時] <────────── [ボーナス終了判定] ──────▶ [AT中]
    ▲                                             │
    └────────── AT終了（G数0 or 完走） ◀──────────┘
                            ※AT中のボーナス当選は [内部中(AT)] を経由し、
                              ボーナス終了後に残りG数+獲得分でATへ復帰
```

状態は `NORMAL / CARRYOVER / BIG / REG / AT / CARRYOVER_AT` の6値で管理し、セーブデータに含める。

## 10. 出玉設計・検算

### 10.1 機械割の計算式
```
機械割 = ( 小役期待枚数/G + ボーナス期待枚数/G + AT期待枚数/G ) ÷ 3
小役期待枚数/G   = Σ( count_i / 65536 × 払い出し_i )
ボーナス期待枚数/G = P(BIG)×190 + P(REG)×56
AT期待枚数/G     = P(BIG) × AT突入率 × 平均AT G数 × 0.5
```

### 10.2 初期値の検算結果（技術介入なし・スイカ完全取得時）

| 設定 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 機械割 | 95.2% | 96.2% | 97.6% | 99.1% | 100.9% | 102.9% |

技術介入（ビタ押し成功によるAT G数上積み ≒ +2〜3%）を加味したフル攻略時の目標値: **設定1 ≒ 97.5%／設定6 ≒ 105.5%**。

### 10.3 チューニング手順
1. 上記の解析値計算をスプレッドシート化（テーブル数値→機械割の自動算出）
2. 実装後、**モンテカルロシミュレーション（設定ごとに1000万G）**を実行
3. 解析値とシミュレーション値の乖離が±0.3%以内であることを確認
4. 目標機械割に対する調整は「単独REGのカウント」「AT突入率」「AT平均G数」の3パラメータで行う（小役は触らない＝コイン持ちを固定）

## 11. システム仕様

### 11.1 アーキテクチャ（レイヤー分離）
```
┌─────────────────────────────┐
│  Presentation層（UI・演出・サウンド）      │  サブ基板に相当
├─────────────────────────────┤
│  Game層（状態遷移・AT管理・二次抽選）      │
├─────────────────────────────┤
│  Core層（65536抽選・リール制御・払い出し）  │  メイン基板に相当
└─────────────────────────────┘
```
- Core層は**純粋関数のみ**で構成（入力: 乱数+状態 → 出力: 結果）。UIから完全独立させ、単体でシミュレーション実行可能にする
- 実機同様「Core→Game→Presentationへの一方向データフロー」とし、演出層が抽選結果に影響する経路を作らない

## 12. UI/UX仕様

### 12.1 画面構成（モバイル縦持ち基準）
```
┌──────────────────┐
│ 液晶演出エリア（上部 約40%）      │ ← ボーナス/AT中はここが主役
├──────────────────┤
│ リール表示（中央・最大サイズ）     │ ← 図柄の視認性を最優先
│  [上段][中段][下段] × 3リール      │
├──────────────────┤
│ クレジット / 獲得枚数 / G数 常時表示│
├──────────────────┤
│ [BET]  [レバー]  [停止×3]         │ ← 画面下部・親指到達圏
└──────────────────┘
```

### 12.2 UI原則
- タップターゲットは最小48×48px（停止ボタンはそれ以上）
- レバーオン→リール始動→停止のレスポンスを最優先（演出のためにタップ反応を遅延させない）
- クレジット・払い出し・G数は常時可視
- 通常→チャンス→ボーナス確定で画面の色調・情報量が段階的に変化する視覚設計
- 目押し補助機能（図柄スロー表示/オートビタ）をオプションとして用意し、初心者と技術介入派の両方に対応

### 12.3 データ表示機能
- スランプグラフ、ボーナス履歴、小役カウンター（チェリー+REG等の設定推測要素）を搭載し、「設定推測遊び」を成立させる

## 13. 演出仕様（方針）

- 演出はPresentation層の抽選（分母256）で決定し、**成立役に対する期待度の法則性**（例: 演出Aは強レア役時のみ発生＝ボーナス濃厚）をテーブルで定義
- 告知タイプ: リーチ目による完全告知を軸に、先告知（フラッシュ）/後告知を織り交ぜる
- 矛盾演出（法則崩れ）＝ボーナス確定、のパターンを意図的に設計する

### 14.8 制作ノート
- 制作開始前に**スタイルガイド1枚**（配色・線の質感・光の表現の基準となるキービジュアル）を確定し、全素材のトーンを統一する
- 実在の遊技機・既存作品・既存キャラクターを想起させる意匠は使用不可。図柄・キャラクターはすべてオリジナルデザインとする
- 発光差分は「同一構図・光のみ変化」で制作する（差分アニメーションの品質が安定する）
- ループ動画は書き出し後に先頭・末尾の連結確認を必ず行う

## 付録: 用語定義
- **フラグ**: レバーオン時の抽選で決定される成立役
- **持ち越し**: ボーナスフラグが入賞まで保持されること（小役は当該ゲーム限り）
- **重複当選**: 1回の抽選で小役とボーナスが同時成立するフラグ
- **リーチ目**: ボーナス成立時にのみ停止し得る出目
- **純増**: 投入分を差し引いた1Gあたりの実質増加枚数
